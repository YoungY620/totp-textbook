# S/KEY and RFC 1760: Engineering the Hash-Chain One-Time Password

<div class="source-card">
<p><strong>Source:</strong> Neil Haller. <em>The S/KEY One-Time Password System</em>. RFC 1760, Bellcore, February 1995 (Informational). <a href="https://www.rfc-editor.org/rfc/rfc1760.txt">Original text</a> — with <a href="https://www.rfc-editor.org/rfc/rfc2289.txt">RFC 2289</a> as the standards-track companion.</p>
<p><strong>In one sentence:</strong> RFC 1760 turns Lamport's idea into a deployable system — MD4 hash chains, a server-issued seed, a 64-bit output shown as six English words, and a challenge–response protocol — using only single-use passwords so that an eavesdropper cannot replay what it captures.</p>
</div>

<div class="hook">
<p>A login to a UNIX host around 1995 no longer asks for your password. The host prints one line — the challenge `s/key sequence_integer seed` — and what you must type back is not your pass-phrase but six short English words. Anyone watching can copy all six down, and it does them no good: the next login wants a different six. What crosses the wire is a value that has already been spent, and the chain only runs in one direction.</p>
</div>

## 1. Background and the problem

RFC 1760 opens with the threat that motivated it: "One form of attack on computing system connected to the Internet is eavesdropping on network connections to obtain login id's and passwords of legitimate users. The captured login id and password are, at a later time, used gain access to the system." The S/KEY system is built to counter this specific attack, which the document calls a *replay attack*.

Its two selling points are stated up front. First, "only a single use password ever crosses the network," and the pass-phrase "never crosses the network at any time, including during login or when executing other commands requiring authentication such as the UNIX commands `passwd` or `su`." Second, "no secret information need be stored on any system, including the host being protected."

The scope is drawn just as explicitly. S/KEY "protects against external passive attacks against the authentication subsystem. It does not prevent a network eavesdropper from gaining access to private information, and does not provide protection against 'inside jobs' or against active attacks where the potential intruder is able to intercept and modify the packet stream." It is authentication against a passive wiretapper, not a secure channel.

The document is candid about its lineage: "The idea behind S/KEY authentication was first proposed by Leslie Lamport. The specific system described was proposed by Phil Karn, who also wrote most of the reference implementation." RFC 1760 is therefore Lamport's 1981 construction, made concrete and shippable.

## 2. Core content

**The secure hash function.** RFC 1760 defines a secure hash function as "a function that is easy to compute in the forward direction, but computationally infeasible to invert," and builds S/KEY on the MD4 message-digest algorithm (Rivest, RFC 1320). The document notes that MD5 was released after S/KEY entered use, but MD4 was kept because so many client programs had already shipped; some sites built equivalent systems on MD5. Clients and hosts must use the same function to interoperate.

**Sixty-four-bit passwords.** MD4 accepts an arbitrary number of bits and produces 128 bits. S/KEY's password is only 64 bits: the output is folded by exclusive-OR of the two 8-byte halves. Sixty-four bits was judged "long enough to be secure and short enough to be manually entered."

**The preparatory step.** The pass-phrase, of any length, is combined with a *seed* the server sends in clear text; this lets one pass-phrase serve several machines (each with a different seed) and lets it be recycled safely by changing the seed. The concatenation is hashed and folded to 64 bits. In pseudocode (from the RFC's code fragment), the seed is written first:

```text
buf = seed || passphrase
d   = MD4(buf)                # 128 bits
S   = fold_to_64(d)           # XOR the two 8-byte halves
```

**Iterating the chain.** A one-time password sequence is produced by applying the secure hash function repeatedly to the preparatory value $S$. RFC 1760: "the first one-time password is produced by passing $S$ through the secure hash function a number of times ($N$) specified by the user. The next one-time password is generated by passing $S$ through the secure hash function $N-1$ times." Writing $H$ for the hash, the passwords are therefore $H^{N}(S), H^{N-1}(S), \dots, H^{1}(S)$, used in that order; the count decreases by one on every login, and an eavesdropper who has seen one password "would not be able to generate any succeeding password because doing so would require inverting the hash function."

**Human-readable output: six words.** Sixty-four bits is awkward to type. S/KEY converts the value into "a sequence of six short (1 to 4 letter) English words. Each word is chosen from a dictionary of 2048 words; at 11 bits per word, all one-time passwords may be encoded." The standard 2048-word dictionary is attached to the RFC, and all hosts and calculators must use it. (RFC 2289 later adds a two-bit checksum carried in the last word, and accepts hexadecimal output as an alternative; RFC 1760 itself mainly specifies the six-word form and lets calculator programs poke the password into the input stream.)

**Challenge and response.** The host issues a *challenge* carrying the current parameters — the sequence number and the seed — in a fixed format so that automated clients can recognise it:

```text
s/key sequence_integer seed
```

Given the challenge and the secret pass-phrase, the client computes (or looks up) the corresponding one-time password and sends it.

**Verification and stored state.** The host keeps a file — `/etc/skeykeys` in the reference implementation — that, for each user, holds the one-time password from the last successful login, or has been initialised with the first password of a fresh sequence by the `keyinit` command. To verify an attempt, "it passes the transmitted one-time password through the secure hash function one time. If the result of this operation matches the stored previous one-time password, the authentication is successful and the accepted one-time password is stored for future use." The server stores one value, checks with one hash, and updates on success.

**Reinitialisation.** Because the client's iteration count falls by one each time, "at some point the user must reinitialize the system [or] be unable to login again." The `keyinit` command lets the user change the pass-phrase, the iteration count, and the seed; the RFC notes a common technique of incrementing a trailing digit of the seed and resetting the iteration count "to something in range of 500-1000."

**Clients.** The reference implementation includes command-line calculators for UNIX and PC (`key`), TSR programs for PCs (`ctkey`, `termkey`, `popkey`), and GUI utilities for Macintosh and Windows (`keyapp`); the most automated, `termkey`, scans the screen for the challenge and inserts the password into the keyboard buffer.

## 3. Threat analysis

**Eavesdropping.** Only single-use passwords cross the wire, never the pass-phrase. From a captured password the adversary cannot produce the next one, because that requires inverting the hash function; the chain direction guarantees that eavesdropping yields only passwords already spent.

**Replay.** Each password is accepted once and then superseded; the server's stored value advances after every success, so a captured value replayed later cannot match.

**Dictionary and exhaustive search.** The pass-phrase is the secret and the seed is public, so the strength of the system depends on the pass-phrase. RFC 1760 advises that the pass-phrase "should be more than eight characters"; RFC 2289 hardens this, requiring at least 10 characters to reduce the risk from exhaustive search and dictionary attacks.

**Compromise of the server's stored value.** Because the server keeps only the last one-time password and never the pass-phrase, an intruder who reads that file does not learn a future password: deriving the next one would again require inverting the hash function. This is the property the document advertises — "no secret information need be stored on any system."

**What is outside the model.** S/KEY gives no confidentiality, does not stop an "inside job," and does not defend against active attacks. RFC 2289 repeats this and recommends IPsec against session hijacking.

<div class="aside">
<p><span class="aside-label">Aside · Why exactly six words</span></p>
<p>Sixty-four bits is awkward to read aloud, so S/KEY spells it as six short English words drawn from a fixed 2048-word dictionary. The size is not arbitrary: 2048 = $2^{11}$, exactly eleven bits per word, so six words carry 66 bits — enough to cover the 64-bit password with room to spare. RFC 2289 later put a two-bit checksum into the last word, so a mistyped password can be caught before it is sent.</p>

## 4. Relation to Lamport, and limitations

**What S/KEY adds to Lamport.** The underlying construction is Lamport's: a one-way hash chain used in the reverse direction, with the server storing a single value and checking with one hash application. S/KEY's contributions are the engineering decisions that make it deployable: it fixes the hash function (MD4, later MD5 and SHA-1 variants), the output size (64 bits, folded down from MD4's 128), and the human encoding (six words from a shared 2048-word dictionary). It introduces the clear-text *seed* as a first-class parameter, so one pass-phrase can serve many machines and be safely recycled, and makes the *iteration count* a user-visible, initialised parameter rather than an abstract chain length.

**Limitations.**
- *Finite chain.* A sequence of $N$ passwords supports a bounded number of logins; when it runs out the system must be reinitialised, which interrupts service and repeats the setup problem. In practice $N$ is set to the low hundreds to low thousands (the RFC's example range is 500–1000).
- *Replay window and concurrency — the race attack.* RFC 1760 describes a fixed sequence of logins, but says little about an adversary who interferes with it. RFC 2289 addresses this directly: an attacker can "listen to most of a one-time password, guess the remainder, and then race the legitimate user to complete the authentication," with guesses against the last word of the six-word form being especially likely to succeed. The recommended defence is to forbid multiple simultaneous authentication sessions, with a timeout to prevent denial of service. The related desynchronisation problem — a lost response leaving the server and client out of step — must be resolved by skipping the challenge *forward*, never by repeating it, since a repeated challenge lets an eavesdropped response be replayed.
- *Manual reinitialisation.* Reinitialising requires the user to present a freshly generated password out of band, and RFC 2289 insists that the seed or the pass-phrase be changed at each reinitialisation.
- *Aging primitives.* RFC 2289 warns that MD4 is generally believed weaker than MD5 and that a server supporting several algorithms "is only as secure as the weakest algorithm"; the design's security is only as good as the chosen hash.

## 5. Related literature

- **L. Lamport, "Password Authentication with Insecure Communication," CACM 24(11), 1981** — the original hash-chain one-time password scheme that S/KEY implements; RFC 1760 credits it explicitly. <https://doi.org/10.1145/358790.358797>
- **N. Haller, C. Metz, P. Nesser, M. Straw, "A One-Time Password System," RFC 2289, 1998** — the standards-track OTP system that obsoletes RFC 1938 and generalises S/KEY: adds MD5 and SHA-1, a checksum in the word encoding, hexadecimal input, the `otp-` challenge format, and the race-attack defence. <https://www.rfc-editor.org/rfc/rfc2289.txt>
- **D. Kogan, N. Manohar, D. Boneh, "T/Key: Second-Factor Authentication from Secure Hash Chains," CCS 2017** — modernises S/Key into a time-based system with no server-side secret, plus a formal lower bound on inverting hash chains and a low-memory client traversal algorithm. <https://arxiv.org/abs/1708.08424>
- **D. M'Raihi, M. Bellare, F. Hoornaert, D. Naccache, O. Ranen, "HOTP: An HMAC-Based One-Time Password Algorithm," RFC 4226, 2005** — the next step in standardisation: HMAC-based one-time passwords with a counter, a shared secret on both sides, throttling and resynchronisation requirements. <https://www.rfc-editor.org/rfc/rfc4226.txt>
- **D. M'Raihi, S. Machani, M. Pei, J. Rydell, "TOTP: Time-Based One-Time Password Algorithm," RFC 6238, 2011** — turns HOTP's counter into a time step, the algorithm behind today's authenticator apps; the direct descendant of the S/KEY line. <https://www.rfc-editor.org/rfc/rfc6238.txt>
- **R. Rivest, "The MD4 Message-Digest Algorithm," RFC 1320, 1992** — the hash function S/KEY is built on, and the reason the 128-bit digest had to be folded to 64 bits. <https://www.rfc-editor.org/rfc/rfc1320.txt>

## 6. Summary and Callbacks

- RFC 1760 (Haller, Bellcore, 1995) engineers Lamport's hash-chain one-time password into a deployable system, crediting the idea to Lamport and the specific system to Phil Karn.
- It targets eavesdropping/replay on the login channel: only a single-use password ever crosses the network, and the pass-phrase never does.
- The hash function is MD4 (RFC 1320); its 128-bit output is folded to a 64-bit password, and the pass-phrase is mixed with a clear-text server seed before the chain is built.
- The chain is $H^{N}(S), H^{N-1}(S), \dots$ — the iteration count drops by one per login — and the 64-bit result is shown as six words drawn from a shared 2048-word dictionary.
- The protocol is challenge–response: the server sends `s/key sequence_integer seed`, the client replies with the matching password, and the server verifies by hashing the reply once and comparing with the stored previous password.
- The server holds only the last password — no pass-phrase, no reusable secret — so compromise of its store yields no usable password; and captured passwords cannot be replayed.
- Limits: a finite chain requiring manual reinitialisation, a race window against a partially observed password (fixed in RFC 2289 by serialising sessions), forward-only resynchronisation, and dependence on the strength of the chosen hash.

**Callback.** S/KEY is where the book's first move gets engineered. Chapter 1 took the secret off the server; this chapter shows what it costs to actually ship that idea — a fixed hash, a folded 64-bit output, a clear-text server seed so one pass-phrase can serve many machines, and a challenge–response exchange people can run over telnet. The host still keeps no reusable secret, and the six-word encoding makes the whole thing usable. That is the good news, and the hook for what follows is its price: a finite chain that must be reinitialised by hand, forward-only resynchronisation, and a login exchange that trusts whoever sends the challenge. The next chapters show what happens when convenience pushes a shared secret back onto the server — the motif's second movement.
