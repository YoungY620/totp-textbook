# The First Systematic Analysis of Browser Password Managers (2014)

<div class="source-card">
<p><strong>Source:</strong> Zhiwei Li, Warren He, Devdatta Akhawe, Dawn Song, University of California, Berkeley. <em>The Emperor's New Password Manager: Security Analysis of Web-based Password Managers</em>. In: Proceedings of the 23rd USENIX Security Symposium, San Diego, CA, August 2014, pp. 465–479. <a href="https://www.usenix.org/system/files/conference/usenixsecurity14/sec14-paper-li-zhiwei.pdf">Open-access PDF</a> (USENIX).</p>
<p><strong>In one line:</strong> The first systematic security analysis of five popular <em>web-based</em> password managers finds critical flaws in all five and enough to steal a user's credentials for arbitrary websites in four of the five — showing that the failure is in implementation and web-platform assumptions, not in the idea of a password manager.</p>

<div class="hook">
<p>Think about the last password you typed. You remember the login box — but the login box is only one of the many places that string has been. Before you typed it, some program generated it, stored it, synced it to a server and filled it in on demand; along the way the same characters pass through JavaScript, through an iframe, and through a website you never consciously chose to trust. The question a 2014 paper asked was blunt: when one program holds the password for every account you own, what does an attacker who has merely gained a foothold in your browser actually get?</p>
</div>

## 1. Background and motivation

Password-based authentication on the web is insecure largely because of the cognitive burden: users, quite rationally, reuse short, guessable passwords across many sites. A password manager is the proposed way out. It stores a distinct, strong password per site, retrieves it on demand, and — because it selects a credential by looking at the page's URL rather than at the page's content — also offers some protection against phishing. Add cloud synchronization across devices, and the pitch is large security and usability gains at low deployability cost. A US-CERT publication quoted in the paper calls a password manager "one of the best ways" to track unique passwords and avoid writing them down; mainstream outlets and even technical books recommend them. Adoption followed: LastPass claimed over a million users as of August 2013, and PasswordBox claimed over a million within three months of its May 2013 launch.

An *idealized* password manager is not a real one. Li, He, Akhawe and Song set out to measure the real thing: what happens when a security analysis is aimed at the browser-resident applications that millions already trust with all their passwords? Their motivating worry is stated plainly — a password manager is a *new, untested single point of failure* in the authentication ecosystem, and one implementation flaw can leak every password a user owns at once. Prior work had already shown the same gap for other password replacements such as single sign-on.

The threat model is the **web attacker**: an adversary who controls web servers and DNS domains and can lure the victim to them. The authors extend it slightly for this setting — the victim may even create an account on the attacker's application and use the manager to store its credential, and the attacker may hold accounts on the password manager service and send requests to it directly. The model assumes the password manager's own code is *not* malicious, that the manager does not share Alice's credentials without her asking, and that the user protects the manager with a unique master password.

The security goal is a single invariant — a stored password is accessed only by the authorized user(s) and by the website it is for — decomposed into four goals: **Master Account Security** (an attacker must not be able to authenticate as the user to the manager), **Credential Database Security** (confidentiality, integrity and availability of the stored credentials), **Collaborator Integrity** (the sharing feature must enforce its access-control lists), and **Unlinkability** (using a manager must not let colluding sites track one user across the web; the paper adopts Bonneau et al.'s definition).

What made this work necessary: attacks on password-manager **bookmarklets** had been known since Adida et al. (2009), and Bhargavan et al. had studied encrypted cloud storage, but no one had systematically mapped the attack surface of web-based password managers. All the products were proprietary and code-obfuscated, lacked any published security architecture, and implemented autofill, client-side encryption and one-time passwords each in their own idiosyncratic way — precisely the conditions under which a comprehensive, comparative analysis is needed.

## 2. The sample and the attack surface

The study covers five popular web-based password managers, chosen for a diverse mix of features (Table 1):

- **LastPass** — the most full-featured: bookmarklet, browser extension and website access; one-time passwords and 2FA; sharing. It encrypts usernames and passwords with a key derived as `KDF(mp, mu, 5000, 32)` (master password, master username, 5000 iterations, 32-octet key).
- **RoboForm (Everywhere)** — stores each credential in its own file, named by default after the site's domain; unless the user sets a master password, those files go to RoboForm's servers *in the clear*. Bookmarklet, extension and website; no sharing.
- **My1login** — bookmarklets only, no extensions ("No install needed"); sharing. Its key is unusual: it concatenates `MD5(pheven) + MD5(phodd)` (the MD5 of even- and odd-position characters of the passphrase) to build a 256-bit key.
- **PasswordBox** — extension only; sharing. It derives a key as `KDF(mp, mu, 10000, 32)` and encrypts passwords *only*.
- **NeedMyPassword** — the minimal case: website-only storage, no auto-login, no generation, no sharing, and credentials are not encrypted at all before being sent to the server.

The authors organise the attack surface into four classes, and it is this taxonomy that the rest of the study follows:

1. **Bookmarklet vulnerabilities.** A bookmarklet is a snippet of JavaScript that runs in the *current page's* (possibly malicious) context. Code running on `evil.com` cannot trust any DOM API, because the attacker may have replaced it.
2. **"Classic" web vulnerabilities** — CSRF (the browser shares cookies across origins) and XSS (unsanitised input inserted into the document, which in the web model means full compromise).
3. **Authorization vulnerabilities.** Sharing gives every credential an access-control list; confusing authentication for authorization — e.g. a missing server-side ownership check — lets any user read any credential.
4. **User-interface vulnerabilities.** Because phishing resistance is a headline benefit, a manager that itself trains users into phishable habits is worse than a normal site: one successful phish can expose every credential.

## 3. Security analysis and findings

The headline result: the authors find critical vulnerabilities in **all five** managers, and in **four of the five** an attacker can learn a user's credentials for arbitrary websites. Vulnerabilities appear in very different features — one-time passwords, bookmarklets, shared passwords — and their root causes are equally diverse: logic and authorization mistakes, misunderstandings of the web security model, and the familiar CSRF and XSS. Table 2 summarises what was found where.

**Bookmarklets.** All three managers that offered a bookmarklet — LastPass, RoboForm and My1login — were vulnerable, and in all three cases a user who clicks the bookmarklet on an attacker's site leaks credentials for arbitrary websites. The LastPass case study: when a user installs the bookmarklet, the page creates a random value `_LASTPASS_RAND` and encrypts the master key with it; the server stores the result (`key_rand_encrypted`) and an identifier `h`, and the bookmarklet carries `_LASTPASS_RAND` and `h`. When used, the bookmarklet injects a script from `lastpass.com` (sending `h` and the page's domain `u`), which builds an iframe that fetches `lastpass.com/bml.php?u=dropbox.com` — a resource at a **predictable URI** that returns the encrypted master key *and* the encrypted Dropbox credential. Because the same-origin policy lets any origin include and execute a script from any other origin, the attacker can request that URI, use a JavaScript-hijacking technique (e.g. `Function.toSource`) to extract the values from the loaded script, and decrypt the credential with the stolen `_LASTPASS_RAND` — then repeat for every credential. The same `h` and `_LASTPASS_RAND` are stable across browsers and differ per user, so any site where the user clicks the bookmarklet learns a stable pseudo-identifier, enabling cross-site tracking and linking of a user's multiple accounts (a violation of unlinkability).

**Web vulnerabilities: the LastPass one-time password.** LastPass's OTP is designed so the server never sees the OTP or the master key: the client computes `h = hash(hash(alice|otp)|otp)` and encrypts the master key with `hash(alice|otp)` to produce `rand_encrypted_key`, then sends `h` and `rand_encrypted_key` to the server, which stores the triple and later authenticates by matching `(username, h)`. The setup request (`otp.php`) authenticates the user with **cookies only and carries no CSRF token**, and the server cannot tell whether `rand_encrypted_key` really encrypts the master key. So an attacker who merely knows Alice's username can forge an `otp'`, compute `h'` and a `rand_fake_key`, and submit the CSRF request — after which they can log in "as Alice" using `otp'`. They cannot decrypt the real master key, but they obtain three things: (1) the list of entry points, which LastPass stores **unencrypted**, so the attacker learns which sites Alice has accounts on; (2) the encrypted database itself, available for offline guessing of the memorised master password; and (3) denial of service — being logged in as Alice, they can delete credentials despite being unable to read them. The paper also reports CSRF in RoboForm (letting an attacker update, delete and add arbitrary credentials) and XSS in NeedMyPassword (complete account takeover); the details of these two are in the extended technical report.

**Authorization. Two of the three sharing managers confuse authentication with authorization.** In **My1login**, the client encrypts a shared credential under the recipient's public key, but the server, when Alice shares a web card, checks only that Alice is authenticated — never that Alice *owns* the card identified by `wcid`. Worse, web-card IDs are globally unique, auto-incrementing integers. The resulting "share-and-update" attack: Mallory shares an arbitrary (even not-yet-existing) card ID with her collaborator Eve using dummy credentials; Eve is thereby registered as a collaborator. Later, whenever the real owner updates that card, the client re-encrypts the genuine credential to *every* collaborator — including Eve. The same flaw lets Eve inject credentials (a login-CSRF variant) or wrong credentials. In **PasswordBox**, the same class of bug appears via `asset_id`, also a globally unique auto-incrementing number (the paper infers PasswordBox managed over 4 million assets from it). PasswordBox *did* implement CSRF defenses (a `Referer` check and an `X-CSRF-Token` header), so the defect was pure logic: sharing never checked ownership, letting Mallory iterate over all `asset_id`s and share every asset to Eve. And because PasswordBox encrypts **only the password field** — full name, username, URL and creation time are plaintext — the disclosure of every user's metadata is itself a severe privacy breach.

**User interface.** When a user is not logged in, a secure design should ask them to open a new tab and log in. Only My1login did this. The RoboForm bookmarklet instead shows a login form in an iframe embedded in the surrounding (attacker-controlled) page, so the URL bar never reads `roboform.com` — training users precisely against the one habit that is safe. An attacker can block the iframe and spoof the dialog; a side channel (the iframe is taller than 200 px exactly when the user is logged in) makes the spoof convincing. LastPass had a similar problem.

**Disclosure.** All attacks were verified experimentally and reported to the affected vendors in the last week of August 2013. Four of the five vendors responded within a week; NeedMyPassword never responded. Apart from the linkability issues and NeedMyPassword's bugs, all the described vulnerabilities were fixed within days. None of the managers ran a bug bounty.

## 4. Applicability and transfer boundaries

The subject of this paper is a specific architecture — the **web-based (cloud) password manager**: credentials synced to a service and reached through a browser extension, a website, or a bookmarklet. Almost every finding is a property of that architecture, not of password managers as such. Two consequences follow.

**What does not transfer.** The largest class — bookmarklet vulnerabilities — exists only where a manager runs its code in a third-party page's JavaScript context. A local-only product (the paper explicitly excludes RoboForm Desktop) and today's browser-native managers (Chrome, Edge, Safari, Firefox) simply do not have that surface, so their specific bugs do not carry over. Likewise, "secrets in JavaScript files" and predictable resource URIs were problems of that deployment model; a native extension with isolated APIs does not expose them in the same way — which is exactly the fix (browser-provided isolated DOM APIs, or an iframe in the manager's own origin) the authors recommend.

**What does transfer.** Several findings are structural and outlive any version: (a) client-side crypto in a web origin must keep secret material out of any script another origin can include, or the encryption is undone by the *serving* design; (b) a sharing feature needs genuine ownership checks, and *predictable identifiers* turn a single missing check from an attack on one user into an attack on all users; (c) a UI that accepts a master password inside an embeddable frame trains users into the one habit that defeats phishing resistance. This is why the recommendations are deliberately broad: CSRF tokens (or the `X-CSRF-Token` header, since an extension cannot easily fetch a fresh token per form) plus `Referer`/`Origin` checks; CSP (only LastPass shipped one, and its policy was weak, allowing `eval` and inline scripts); serve scripts that are identical for all users and keep secrets in HTML or JSON; cryptographically random identifiers instead of consecutive integers; and a simpler, single-owner sharing model that makes missing authorization checks stand out.

**Preconditions.** The attacks assume the web-attacker model: control of a site the victim visits, or an account on the manager service. They need no local malware, no network position and no malicious manager code. Notably, the authorization attacks (My1login, PasswordBox) and the LastPass OTP attack need **nothing from the victim's browser at all** — only knowledge of a username or an ID — which shows that "the server only ever sees ciphertext" is not by itself a security argument.

**Limits, as the paper frames them.** The analysis is manual, so the authors expect undiscovered bugs; the sample is five proprietary, obfuscated products from 2013; some attack details live in an extended technical report rather than the conference paper; and the encryption studied protects only the *credential* fields, leaving metadata (URLs, usernames, full names) frequently in the clear — a theme that returns in the next chapters. The direct lesson for today: browser built-in managers and standalone apps still face autofill/injection and metadata-leak questions, but through different surfaces (native autofill frameworks, mobile-OS integration), which is precisely what later work takes up.

<p>The paper is called <em>The Emperor's New Password Manager</em>, a deliberate echo of Hans Christian Andersen's <em>The Emperor's New Clothes</em>: a whole crowd praises garments that are not there, because admitting you cannot see them would expose you as unfit for your post. ## 5. Related literature and the state of the field

The authors position themselves as **systematisers and critics** of the "idealized password manager" narrative: they accept the framework that says managers *should* help (Bonneau et al.) but demonstrate that real implementations "critically undermine" it.

- **J. Bonneau, C. Herley, P. C. van Oorschot, F. Stajano, *The Quest to Replace Passwords: A Framework for Comparative Evaluation of Web Authentication Schemes*, IEEE S&P 2012** ([IEEE](https://doi.org/10.1109/SP.2012.44)) — supplies the framework and the unlinkability definition; it highlights the advantages of an idealized manager, which this paper then meets with real-world flaws.
- **B. Adida et al., *Attacks on password manager bookmarklets*, 2009** — the earlier bookmarklet attacks; Li et al. show the problems persisted and that, once managers encrypt credentials client-side, a new iframe-based defense is required.
- **K. Bhargavan et al., *Defensive JavaScript / encrypted cloud storage*** — studied five password managers and other encrypted-cloud services, inspired a redesign of the LastPass bookmarklet, and produced Defensive JavaScript, the only prior work the authors cite that protects a JavaScript gadget from its host page.
- **M. Blanchou, P. Youn (iSEC Partners), *Password managers: Exposing passwords everywhere*, 2013** ([PDF](https://www.isecpartners.com/media/106983/password_managers_nov13.pdf)) and **Silver et al. (concurrent work)** — found flaws in password-manager **autofill**; Li et al. cover a broader range of features but only third-party web-based managers.
- **D. Belenko et al., *mobile password manager cryptographic properties*** — brute-forcing mobile managers, an adjacent device-side threat.

Subsequent work has kept the question open and moved to new surfaces:

- **S. Oesch, S. Ruoti, *That Was Then, This Is Now: A Security Evaluation of Password Generation, Storage, and Autofill in Browser-Based Password Managers*, USENIX Security 2020** ([usenix.org](https://www.usenix.org/conference/usenixsecurity20/presentation/oesch)) — five years on, re-evaluates generation, storage and autofill (this book, chapter 9).
- **M. Carr, S. F. Shahandashti, *Revisiting Security Vulnerabilities in Commercial Password Managers*, SEC 2020** ([arXiv:2003.01985](https://arxiv.org/abs/2003.01985)) — revisits commercial managers' vulnerabilities.
- **S. Oesch, A. Gautam, S. Ruoti, *The Emperor's New Autofill Framework: A Security Analysis of Autofill on iOS and Android*, ACSAC 2021** ([arXiv:2104.10017](https://arxiv.org/pdf/2104.10017)) — carries the "emperor's new clothes" framing to mobile autofill frameworks.
- **A. Fábrega, A. Namavari, R. Agarwal, B. Nassi, T. Ristenpart, *Exploiting Leakage in Password Managers via Injection Attacks*, USENIX Security 2024** ([usenix.org](https://www.usenix.org/conference/usenixsecurity24/presentation/fabrega)) — the injection/leakage line that builds directly on the sharing-and-sync concerns first raised here (this book, chapter 10).

Across this literature the field has converged on the judgement this paper first argued in detail: the *concept* of a password manager is sound and its risks are concentrated in **implementation and the surrounding platform**, not in the algorithm; and "the server only sees ciphertext" is a claim that must be checked at the level of every feature, every identifier and every script the service serves. The authors' own closing agenda — automated vulnerability-discovery tools and a principled, secure-by-construction password manager — remains largely open.

## 6. Summary and Callbacks

- This is the first **systematic** security analysis of **web-based** password managers; the sample is five products: LastPass, RoboForm (Everywhere), My1login, PasswordBox and NeedMyPassword.
- Threat model: the **web attacker**; four security goals — master-account security, credential-database security, collaborator integrity, and unlinkability.
- The attack surface is split into four classes: **bookmarklet**, **classic web (CSRF/XSS)**, **authorization**, and **UI** vulnerabilities.
- Result: critical vulnerabilities in **all five**, and in **four of five** an attacker can steal a user's credentials for arbitrary websites.
- Representative attacks: the LastPass bookmarklet leak (predictable `bml.php` URI + JS hijacking, plus linkability via `h`/`_LASTPASS_RAND`); the LastPass **OTP CSRF** (no token; leaks the plaintext entry-point list, enables offline guessing and DoS); My1login/PasswordBox **missing ownership checks** on auto-incrementing IDs (share-and-update); and RoboForm's **iframe login form** as a phishing anti-pattern.
- Recommended fixes are broad and defense-in-depth: isolated DOM APIs / an iframe architecture for bookmarklets, CSP, CSRF tokens plus `Referer`/`Origin` checks, no user-specific JS, cryptographically random identifiers, and single-owner sharing.
- Publication ethics: reported in August 2013; four of five vendors responded and all non-linkability bugs were fixed within days; NeedMyPassword never responded.
- The boundary: the findings are specific to the *web/cloud, browser-resident* architecture — browser-native managers and standalone apps lack the bookmarklet surface — but the structural lessons (client-side crypto in a web origin, authorization on sharing, predictable IDs, phishable login UI) transfer, and later work (2020–2024) continues along the same fault line.

**Callbacks.** This chapter opens the book's fifth act, and it turns the whole book's question around to look at it from the other side: *when the server cannot be trusted, where do the secrets live?* Lamport's answer (chapters 1–2) was to take the secret off the server; HOTP and TOTP (chapters 3–4) put a **shared** secret back on both sides; chapter 6 watched the damage move into implementations; T/Key (chapter 5) tried to take it away again. The 2014 managers arrive selling the comfortable version of the same bargain — a strong, unique password for every site, synced to all your devices through a service that supposedly cannot read them — and they reproduce the pattern at once: the secret is back in a centre of trust, and the failure is again in implementation and platform, not in the idea. What is new is that the advertised property now has a name — *zero knowledge* — so the distance between the promise and the code becomes this act's subject for chapters 9–12.
