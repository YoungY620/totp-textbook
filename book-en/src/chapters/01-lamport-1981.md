# Password Authentication with Insecure Communication: Lamport, 1981

<div class="source-card">
<p><strong>Source:</strong> Leslie Lamport. <em>Password Authentication with Insecure Communication</em>. Communications of the ACM, 24(11), pp. 770–772, November 1981. DOI: <a href="https://doi.org/10.1145/358790.358797">10.1145/358790.358797</a></p>
<p><strong>In one sentence:</strong> By making every password a link in a one-way hash chain and letting the server keep only a single value, the paper turns a password that crosses a channel an adversary can read and modify into something usable exactly once, defeating eavesdropping and replay.</p>
</div>

<div class="hook">
<p>A login in 1981: the user types a password at a terminal, and somewhere along the wire an eavesdropper copies it down. Nothing has gone wrong — the password is the right one, the host checks it, the login succeeds. The next night the eavesdropper types the same password and is let in. Every value the channel carried was genuine; the flaw was that a genuine value could be used twice.</p>
</div>

## 1. Background and the problem

Ordinary password authentication has a structural weakness: the password itself travels. Anyone who can read the traffic — a wiretapper on a shared line, an operator, a compromised router — obtains the credential and can present it again later. Hashing the password file on the server defends against theft of the server's database, but it does nothing about the wire, because the plaintext password still crosses the network on every login.

Lamport's 1981 paper isolates this setting and names it. Its published abstract states the threat model and the promise in two sentences: the method "is secure even if an intruder can read the system's data, and can tamper with or eavesdrop on the communication between the user and the system"; and it "assumes a secure one-way encryption function and can be implemented with a microcomputer in the user's terminal." Three adversarial capabilities are therefore *granted* to the attacker: reading the server's stored data, eavesdropping on the channel, and modifying messages on the channel. The single capability the scheme is allowed to assume is absent is inverting the one-way function.

The design goal follows directly: a password scheme in which every value that crosses the wire is useless to an eavesdropper and useless if replayed, and in which a stolen server database yields no usable password.

*Availability of the source.* No open-access copy of the original paper was located; ACM hosts it behind a paywall, and no legitimate free copy was found. The account below rests on the paper's published abstract and on public material that describes and credits Lamport's technique — chiefly RFC 1760, whose Acknowledgements attribute the idea to Lamport, and the Cornell CS513 lecture notes that follow the paper. Claims that are more specific than these sources are labelled as such.

## 2. Core content: one-way hash chains

**The one-way function.** The scheme assumes a function $F$ that is easy to compute in the forward direction and computationally infeasible to invert: given $x$, computing $F(x)$ is cheap, while recovering $x$ from $F(x)$ is not possible within the assumed effort. Nothing else is assumed — the same "secure one-way encryption function" the abstract refers to.

**Building a chain.** The user picks a secret $s$ (a seed) and an integer $n$ (the chain length) and computes

$$x_{0} = s, \qquad x_{i} = F(x_{i-1}) \quad \text{for } i = 1, 2, \dots, n .$$

So $x_{i} = F^{i}(s)$: the value at position $i$ is $i$ successive applications of $F$ to the seed. The chain has a direction. From $x_{i-1}$ one obtains $x_{i}$ by one evaluation of $F$; from $x_{i}$ one cannot obtain $x_{i-1}$ without inverting $F$. Moving toward higher indices is easy; moving toward lower indices is the hard direction.

**Using the chain in reverse.** The scheme exploits exactly this asymmetry by presenting the passwords in the direction an adversary cannot travel — the most-hashed values first:

$$x_{n}, \; x_{n-1}, \; x_{n-2}, \; \dots, \; x_{1} .$$

Each password is one $F$-step "behind" the previous one: after $x_{i}$ has been used, the next password to send is $x_{i-1}$, and $x_{i-1} = F^{-1}(x_{i})$, which requires inverting $F$. RFC 1760 states the rule the same way, in terms of a starting value $S$: "the first one-time password is produced by passing $S$ through the secure hash function a number of times ($N$)... The next one-time password is generated by passing $S$ through the secure hash function $N-1$ times." The count decreases by one on each login.

**Server-side verification and state.** The server never stores the seed $s$. It keeps one value per user, and that value is always "one $F$-step ahead" of the next password it will accept. To authenticate a received password $v$, the server evaluates $F$ once and compares:

$$F(v) \;=\; \text{(stored value)} .$$

If the check holds, $v$ is the correct next password; the server accepts and replaces the stored value with $v$. RFC 1760 describes precisely this: the host "passes the transmitted one-time password through the secure hash function one time. If the result of this operation matches the stored previous one-time password, the authentication is successful and the accepted one-time password is stored for future use." The server is initialised out of band with the appropriate starting value (the top of the chain, $x_{n}$, or equivalently one step ahead of the first password it will accept). Whether that initial value is counted as the first password or as a separate anchor one step ahead is a bookkeeping convention; both RFC 1760 and RFC 2289 describe the same mechanism.

Because the stored value advances after every successful login, each password is genuinely single-use.

## 3. Security analysis

**Eavesdropping.** Suppose the adversary records a login and thereby learns $x_{i}$. To impersonate the user at the next login it must produce $x_{i-1}$, which means computing $F^{-1}(x_{i})$ — inverting the one-way function. This is the only step the security rests on. The adversary can compute *forward* values $x_{i+1}, x_{i+2}, \dots$ from $x_{i}$, but those are passwords the user has already spent and the server has already discarded. The set of values the adversary can reach and the set it needs are disjoint.

**Replay.** Reusing any previously accepted value fails. Verification demands that the received value hash to the *current* stored value; once a login has succeeded, the stored value has already advanced. A replayed old password $x_{i}$ satisfies $F(x_{i}) = x_{i+1}$, which no longer equals the stored value, so it is rejected.

**Compromise of the server's data.** The server holds neither the seed $s$ nor the next password. It holds one link of the chain — a value the user is about to send anyway — and reading it does not reveal a usable password, because deriving the next one would again require inverting $F$. This is the abstract's claim that the method is secure "even if an intruder can read the system's data."

**Tampering with the channel.** A modified password is rejected by the same one-step check, so an adversary cannot forge an accepted password by editing traffic. The scheme authenticates a password value; it does not, on its own, provide confidentiality or protect against active denial of service. The paper's model grants the intruder the ability to tamper, and the chain check is what keeps a tampered exchange from succeeding.

**A known refinement: protecting the challenge.** The construction has one subtlety that later analyses of the scheme single out. Since the client stores the seed, it will compute *any* chain value on request, and from a value near the seed end one can compute the rest of the chain by iterating $F$. If the client accepts a challenge (the index it is asked to answer) from an unauthenticated source, an attacker impersonating the server could induce the client to reveal a value close to the seed and thereby derive many of the user's remaining passwords. The defences are for the client to authenticate the source of the challenge, or to track the last challenge it answered and ignore any challenge that jumps implausibly far (Cornell CS513 notes).

## 4. Impact and limitations

**Impact.** The paper is the origin of hash-chain one-time passwords. S/KEY and the OTP standard (RFC 1760, RFC 2289) are direct engineering, and the idea recurs throughout later work: the same one-way-function chaining underlies Lamport's own one-time signature scheme (1979), Merkle's hash trees (1989), hash-chain micro-payments, broadcast authentication, and the modern hash-chain OTP system T/Key (2017). Two practices it introduced persist today: nothing secret needs to be stored on the server, and each credential is valid exactly once.

**Limitations.**
- *Finite chain.* A chain of length $n$ yields a bounded number of logins; when it is exhausted the system must be reinitialised, and the new anchor must be delivered to the server securely. This is the price of never storing a reusable secret.
- *Initial distribution.* The top value $x_{n}$ (and each successor anchor after reinitialisation) must reach the server over an authentic channel, and the seed $s$ must stay secret on the client. The scheme shifts, rather than removes, the trust requirements.
- *No rewinding, no easy resynchronisation.* The stored value only moves forward. If a message is lost, the server and client can fall out of step; the correct recovery is to skip *forward* to a fresh index, never to repeat a challenge, because a repeated challenge would let a captured response be replayed.
- *Client state and trust.* The client must hold the seed and know its position in the chain, and it must not be fooled into revealing a late-chain value, as noted above.
- *Authentication only.* The scheme does nothing for data privacy and is explicitly not a defence against active attacks, as the later RFCs emphasise.

## 5. Related literature

- **N. Haller, "The S/KEY One-Time Password System," RFC 1760, 1995** — the first full engineering of Lamport's scheme: MD4 chains, a public seed, a 64-bit output and a six-word encoding. <https://www.rfc-editor.org/rfc/rfc1760.txt>
- **N. Haller, C. Metz, P. Nesser, M. Straw, "A One-Time Password System," RFC 2289, 1998** — the standards-track OTP system derived from S/KEY; adds SHA-1 support, a checksum in the word encoding, and an explicit defence against the race attack. <https://www.rfc-editor.org/rfc/rfc2289.txt>
- **D. Kogan, N. Manohar, D. Boneh, "T/Key: Second-Factor Authentication from Secure Hash Chains," CCS 2017** — modernises S/Key: time-based, no secret stored on the server, with a lower bound on inverting random-function hash chains and a low-memory traversal algorithm. <https://arxiv.org/abs/1708.08424>
- **L. Lamport, "Constructing Digital Signatures from a One Way Function," SRI CSL-98, 1979** — the sibling idea by the same author: a one-way function used, in a reverse-chaining style, to sign a single message, the ancestor of one-time signatures. <https://www.microsoft.com/en-us/research/publication/constructing-digital-signatures-one-way-function/>
- **R. C. Merkle, "A Certified Digital Signature," CRYPTO '89, LNCS 435, pp. 218–238** — generalises chaining into a hash tree whose single root commits to many one-time keys; the structure reused today in blockchains and certificate transparency. <https://doi.org/10.1007/0-387-34805-0_21>
- **C. Lefevre, B. Mennink, "Permutation-Based Hash Chains with Application to Password Hashing," ePrint 2024/557** — a modern security analysis of hash-chain password systems (S/Key and T/Key), with offline/online adversary separation and multi-user proofs. <https://eprint.iacr.org/2024/557>

## 6. Summary and Callbacks

- The problem: a reusable password sent over an unsecured channel can be captured and replayed, and a stolen server database can leak it.
- The tool: a one-way function $F$, easy forward and infeasible to invert.
- The construction: a hash chain $x_{i} = F^{i}(s)$, presented in reverse order $x_{n}, x_{n-1}, \dots, x_{1}$, so that each password is the hard-to-compute predecessor of the previous one.
- The server keeps a single value, verifies an incoming password with one application of $F$, and then updates that value to the password just accepted.
- Eavesdropping yields only already-spent passwords, and replay fails because the stored value has advanced; a captured server value reveals no usable password.
- Assumed threat model: the intruder may read the server's data and may eavesdrop on or tamper with the channel — but cannot invert $F$.
- Limitations: a finite chain that must be reinitialised, the need to distribute the initial value securely, no backward resynchronisation, and reliance on the client to trust the challenge.
- Legacy: the direct ancestor of S/KEY, RFC 2289 and T/Key, and the shared root of hash-chain signatures and Merkle trees.

**Callback.** This chapter is the origin point of the book's central question: *where should the secret live?* Lamport's answer is to take the secret off the server — the host keeps one link of a chain and never the seed, so what an attacker can steal is a value the user was about to send anyway. That is the first movement of the motif of taking the secret away, putting it back, and taking it away again. It also plants the hook for the next chapter: an idea that is elegant on paper still has to be engineered — a real hash function, a real output size, real people typing it — before anyone can deploy it. And it deliberately leaves openings — a finite chain, an anchor that must be delivered out of band, a client trusted with the seed — that the rest of the book will come back to.
